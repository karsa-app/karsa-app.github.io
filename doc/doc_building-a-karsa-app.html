Building a Karsa app

When a task grows past organizing data into building software — a tool, a dashboard, an automation, a small service — Karsa is where it gets built. Not in a scratch directory. Not against someone else's cloud. Inside the project, on the Karsa SDK.

This is the single most important idea for an agent working in Karsa: the app you build runs caged inside the project, and it talks to infrastructure only through the Karsa SDK. Read this whole page before you scaffold anything.

The shape of a Karsa app

A Karsa app is a per-project program that the daemon runs as a subprocess and surfaces in the UI (today via an iframe). It is caged: it gets capability through a gatekept SDK surface, not raw access to the machine. That cage is a feature — it means an app can be powerful without being dangerous, and it means "expand to the cloud later" is a config change, not a rewrite.

You build the app in the project tree (under karsa/proj_*/), versioned in git like everything else. Its data lives in the project's sqldb/. Its files live in the project. Nothing escapes the cage by default.

The SDK is the whole interface to infrastructure

Everything an app needs from the outside world comes through @karsa/* SDK packages. You do not open sockets, spin up servers, or sign up for external accounts. You call the SDK:

  • @karsa/sqldb — relational storage. This is the sole storage chokepoint: it is what makes a local app able to "expand" to the cloud unchanged. Tabular data, app state, anything you'd reach for Postgres for — it goes here.
  • @karsa/docdb — document storage (markdown-truth documents with a derived index). Built on top of @karsa/sqldb, not its own database. Use it for notes, specs, content — anything document-shaped.
  • @karsa/blob — large binary objects: uploads, images, generated artifacts.
  • @karsa/queue — background work and message passing between parts of your app.
  • Plus the rest of the gatekept surface as you need it: schedule, agents, http, secrets.

Because these are the only doors, the daemon can enforce the cage, swap a local backend for a cloud one, and keep the app portable. An app written to the SDK is an app that survives "let's deploy this for real."

Files-first, indexes derive. Every write lands on disk as the source of truth (a markdown/frontmatter artifact); any SQLite/search index is synced, never authored, and never feeds back — docdb does write-through indexing (file write → immediate DB update), event-driven sync subscribers converge reverse indexes on CRUD, and a boot reconcile is the catch-up. You write the file; the index follows. So a record is always readable from disk alone, and an external edit or a fresh boot re-derives the index — nothing lives only in a database.

How your code executes — two modes

Every fn you (or your app) install runs in one of two modes, chosen by its nature:

  • Pure TS fns (the default). A Deno sandbox with fine-grained permission flags and no --allow-run. The fn cannot spawn processes, open arbitrary sockets, or touch the daemon's internals — its only channel to the server is the fn SDK (defineFn + karsa.op(...), a UDS wrapper over the op registry, gatekept per-call by the fn's permissions). Write your logic; call ops; that's the whole surface.
  • Process-spawning fns (the explicit exception). A few fns exist to run another program — the agent-harness wrappers (claude_code, codex) and app process recipes. Only these get spawn capability, and it's visible in what they are, never a default you inherit.

A fn that should stay hot can declare warm: true (+ idle_timeout_ms): the daemon spawns it once as a supervised long-running process (visible as an exec_, idle-reaped, crash-restarted on the next call), serving calls over a socket that lives right in the fn's own dir — fn/<fn_id>/default.sock (files-first: no hidden state tree; it appears while the fn is running and is cleaned up when it stops — leave it alone and don't commit it). From any fn, karsa.call(fnRef, input) reaches another fn — dialing a warm-running target directly, else falling back to a normal one-shot invoke.

A different agent CLI is just another fn

There is no machine config for pointing Karsa at a different claude/codex build — and none needed. The agent harnesses are ordinary fns, so a custom binary is a fn variant: copy the harness fn's dir (new dir under fn/, fresh record — the daemon mints the id), point it at your binary (the harness fns accept a binary input; a non-TS tool is a runtime: binary fn whose entry names the executable), and reference the new fn from your agent user's fns: list. Ask the planner to do this for you — "create a fn like claude_code but using /path/to/claude-beta" is exactly the kind of change it makes.

Run metadata: the reserved _metadata output field

A fn can report run-level metadata — token counts, cost, durations, anything worth showing on the run's record — by declaring a _metadata property in its output JSON Schema and including it in the returned value. _metadata is reserved: when present, the daemon pulls it off the return value (the caller receives the output without it) and persists it onto the run's exec_ record (metadata: + metadata_source: fn), where the exec detail's Metadata view renders it. No _metadata in your output → nothing happens; there is no separate channel to manage. The agent-harness fns report their token/cost numbers through this same mechanism.

If a fn is also part of an app (stamped app:), it acts as the app's service user — its writes attribute to the app — and its back-calls are gated by the fn's own declared permissions (spec_permissionsMapp:GPXundefinedRDAundefined). See spec_permissionsKXMundefinedXPundefined "App execution model" for the full picture.

How to build, step by step

@karsa/sqldb. Stay in the project. Scaffold the app in the project tree. Do not create it in /tmp, your home directory, or a sibling folder outside Karsa. @karsa/docdb. Pick the right storage. Tabular / relational → @karsa/sqldb. Document-shaped → @karsa/docdb. Files → @karsa/blob. Background jobs → @karsa/queue. Don't introduce a second database. @karsa/blob. Use the SDK for every external need. Need persistence, files, jobs, scheduling? There's an SDK door for it. If you think there isn't, check again before reaching outside — that instinct is usually wrong (see Anti-patterns). @karsa/queue. Keep it caged. Don't try to break out of the cage for "convenience." The cage is what lets the app be trusted and later expanded. karsa/. Version it. It's all plain files under karsa/, in git. Commit as you go.

Local now, cloud later — for free

The reason the SDK matters so much: a Karsa app written against @karsa/sqldb runs locally today and can expand to the cloud without a rewrite, because the storage chokepoint is the seam Karsa controls. The moment you go around the SDK — embed a raw SQLite file, call an external API directly, hardcode a connection string — you break that seam, and "expand" becomes "rebuild."

So: build inside, build on the SDK, and the path to production is already laid.

An app is a caged namespace (spec_undefinedMundefinedXREXundefinedT)

The deepest thing to understand: an app is a caged mini-namespace, not a pile of top-level artifacts. Everything the app owns — its collections, its fns, its subscribers — lives under app/{app_id}/, isolated from the user's and from every other app's. Contrast a template, which is a copy: its artifacts land at the project top level and become yours to edit. An app's artifacts stay the app's.

The cage is the app's world. It has implicit full access to its own subtree, and reaches anything outside only with explicit permission. That single rule — own-namespace-free, everything-else-permissioned — is what makes an app both powerful and safe, and what makes install / reinstall / uninstall clean (they operate on one subtree; nothing collides, nothing duplicates).

Two shapes of app

  • Supervised — a long-running process (the tunnel, @karsa/caffeinate). Its record has a controller fn (fn_app_controller) + config.process, and the daemon converges it. This is the sidecar section below.
  • Event-driven — no supervised process. A subscriber turns events into work by invoking the app's fn. @karsa-app/codex is the first: msg.created → the codex runner fn → a codex CLI turn → a reply. Its app record has no fn at all (app.fn is optional).

Package layout — @karsa-app/{name}

The scope names the shape: @karsa-app/* (caged app) vs @karsa-template/* (copied template) vs @karsa/* (SDK libraries). A caged app package:

codex/
  karsa.package.json          # { "name": "@karsa-app/codex", "kind": "app", "scope": "project" }
  src/
    app/codex/index.md        # the app record (vanity id `tmpl_app_codex`, rewritten on install)
    fn/codex_runner/          # a fn the app owns — descriptor + its code files
      index.md
      runner.ts  lib.ts
    subscriber/sber_codex.md  # binds an event → the fn
    codex-context/index.md    # a collection the app owns (its data)
    codex-instruction/index.md

Install materializes all of that under app/{app_id}_codex/ (the cage), minting one id per record, rewriting tmpl_ vanity refs to the minted ids, and stamping each with its package. Reinstall reconciles that subtree in place — same slug → same id → state preserved, never duplicated. Uninstall removes the subtree.

The app's own code is UDS-only; capability lives in fns

The deepest rule of the cage: an app's own code can do nothing but talk to the UDS. No filesystem, no network, no spawning a subprocess. Everything the app reaches — persistence, another chat, the outside world — goes through the gatekept SDK over that socket. To do anything privileged (run a CLI, call a remote host), the app calls a capability fn, and a fn is the only thing that carries real OS power:

  • The fn declares what it needs. A capability fn does one specific thing and declares its OS permissions: allow: [run, net] (over the read/write/env baseline). The launcher grants exactly that — on any invocation path, so spawning no longer forces "detached."
  • Two gates, cleanly split. A capability fn exists — a fn carrying --allow-run is a privileged artifact, approved at install (you approve the app that ships it) or authored by the owner. May the caller invoke it — the caller holds permission/run/create (optionally scoped { fn: … } to a specific fn, spec_permission/run/createM--allow-runGPX{ fn: … }RDAundefined §undefined). The fn is a neutral capability; the permission is per-caller.

So "what can this app touch outside itself?" = the app-user's permission list (user.permissions), DERIVED at install from its fns. codex's runner is such a fn: allow: [run] (it spawns the codex CLI), and the codex app-user holds permission/run/create (to invoke it) + permission/chat/*, permission/msg/*, … (its fns' declared reach).

Fns are the app's API

An app's public API is its set of exposed fns (app.exports.fn). Anyone permitted executes one through the one primitive, karsa/run/create (gated by permission/run/create) — the app's own subscriber, the cage UI, or another app. Per fn: access: public | private, and a permissions declaration — the permissions the fn HOLDS when it runs (permissions: { docdb: [chat, msg] } → permission/chat/*, permission/msg/*; a flat slug list works too).

A stamped fn (app: tmpl_app_codex) runs as a user the app owns, so every SDK call it makes is caged to that user — and it writes as that user: karsa/msg/create { chat_id, body } stamps _created_by = the acting persona-user, and the chat renders it via that user's display name. There is no write-as / impersonation of users the app doesn't own. An app may own multiple identities (personas) — see below — but a different driver CLI is still a different app (@karsa/claude-code).

The gate is inferred — you declare nothing (spec_undefinedMundefinedGPXundefinedRDAundefined §undefined)

A permission IS an op. Every op is gated by exactly one permission, auto-derived from the op id (permission/msg/create:permission/msg/create): karsa/msg/create needs permission/msg/create. It is inferred, not declared — a collection/index.md states nothing about permissions, and the requirement can't drift from the op because it is the op. permission/full (the owner) always passes.

Scoping lives on the held grant, never the requirement: a held permission may carry attrs that equality-match the op's input — permission/report/update { ownerId: user_X } granted to user_X = "update only your own rows" (row-level access). Values are static for now; dynamic/relational rules (ownerId === whoever is calling) are code in the collection's on_create / on_update api-filters, not a permission attr. So: the requirement is inferred + attr-free; the grant is where you scope.

Addressing (spec_undefinedMundefinedXREXundefinedT §undefined)

  • Bare = your own container, never bubbles. Inside codex, codex-context/list and fn/other resolve in the cage. A name that isn't there is not found — it does not fall through to the project.
  • Cross a boundary with an explicit {type}/{selector}/ prefix: project/_/… (the _ means "my nearest project" — no hardcoded id), project/{slug}/…, app/{slug}/…, or proj_{id}/… / app_{id}/….
  • A record is addressed by id in a named container: the event hands codex msg_2346; it reaches it as project/_/msg_2346. A collection op is {container?}/{collection}/{verb} and the prefix scopes the op — codex writes the chat with karsa/project/_/msg/create { chat_id }.
  • Resolution ⟂ permission: the prefix says where; the app-user's permissions say may-I.

Multiple personas + @mention routing (spec_undefinedMundefinedEundefinedKundefinedQundefinedC)

An app can host several personas — distinct chat identities it owns (codex: "Codex", a "Reviewer", a "Planner"), each with its own instruction and on/off switch. A message routes to a persona by @mention, and routing is purely declarative — no dispatcher, no special "default" subscriber:

  • A persona is a triple the app owns: a user (kind: agent, stamped app: <id>, with a display name + slug = its @handle), a per-persona instruction record, and a subscriber that matches mentionedUsers: <its-slug>. Enable/disable = that subscriber's run_mode (the app-status gate flips them; app/update {status}).
  • msg.mentionedUsers is a core, derived array of user slugs on every karsa/msg/created event — the @slug tokens in the body that resolve to real project users (an email a@b.com is not a mention). A persona's subscriber does an array-includes match on it; that's the whole router.
  • The default falls out of a pointer, not a subscriber. Set default_ai_reply_user_id on the chat collection (project default) or a chat record (per-chat override, chat wins). For an unmentioned human message, fn_msg_create injects that default slug into mentionedUsers — so the default persona's ordinary subscriber fires. An app that ships default_reply: true gets this wired at install (codex → @codex). Any explicit @mention suppresses the injection.
  • The runner learns which persona it is from input.actor (the daemon injects it — the subscriber's pinned user, or the app-user for the default). It keys its state by that persona and replies as it.

So "add a Reviewer" = create the (user + instruction + subscriber) triple; "talk to it" = @reviewer; "turn it off" = pause its subscriber. One code path, N personas.

"Persona" is a convenience, not a primitive (spec_undefinedMundefinedEundefinedKundefinedQundefinedC §undefined)

Unbundle the triple and there is no persona left — only three primitives that each stand alone:

codex-context. a user — the identity (handle, display name, kind, permissions; humans and AI identities are the same primitive); subscriber. app-owned per-user collections — not a core slot at all; "instruction" is just an app collection keyed by user id, and an app stores whatever else it needs the same way (codex keeps codex-context, the per-(user, chat) resume session; your app's data can be any shape); undefined. a subscriber — the invocation mechanism (users are never "invoked"; subscribers fire).

There is no core persona op. codex_persona_add / claude_code_persona_add are each app's own one-call convenience over its own collections — ship one like it if a bundle fits your app, or just make the three API calls directly. A different app composes differently, and that's the point.

The same primitives compose beyond AI replies:

  • A mention-subscriber is a notification system. A human user + a subscriber matching mentionedUsers: <their-slug> running a delivery fn = "@mention someone, their phone pings." A Slack app's outbound half is exactly this — the fn posts to Slack's API through the egress proxy, so the Slack token stays a secret_ the fn never sees.
  • Inbound bridges are the reverse composition. The Slack app creates a per-project ingress (a Karsa Cloud webhook URL), Slack posts to it, the gateway emits karsa/ext/ingress on the project bus, and an app subscriber writes the message via karsa/msg/create. Loop safety falls out: the bridged message is authored by the app-user (author_kind: service), so it never triggers the default-AI injection or author_kind: human matchers — two bridges can't ping-pong. If AI should react to bridged messages, that's the bridge app's explicit choice, not an ambient default.

Apps: packaging a long-running sidecar

Everything above is the per-project app — code that lives in a project. The supervised shape is a Karsa app record — a long-running process of the server itself (one per server, shared by all projects), packaged as an artifact and supervised by the daemon. The reverse tunnel (karsa-tunnel-client) is the first one, and it is the worked example below. The point of this section is the pattern: after reading it you (or your agent) can mint a new app without touching Karsa's core.

The artifact is the desired state

An app is one dir-shaped record in the System project's app collection — an id-named dir app/app_<ULID>_<slug>/index.md (the record carries a reserved _slug; the dir is id-prefixed per the convention), body = the app's README:

id: app_<ULID>
type: app
name: Tunnel
status: disabled        # enabled | disabled — the DESIRED state, the only field you toggle
fn: fn_app_controller   # who converges it (the core controller, or your own fn — see below)
config:                 # non-secret spawn config; becomes argv/env material
  gateway_url: https://gw.karsa.dev
  ws_url: wss://…/tunnel
  uuid: <host uuid>     # the public entrypoint identity (the "host"; the daemon is the "server")
  local_port: 1688
secrets:                # NAMES only — values NEVER live in the record
  - bind_key
  - ingress_secret

You never write "start the process" anywhere. The record is the desired state; machinery converges reality to it.

App anatomy — the stamp is the manifest

> An app never introduces new kinds of things — it installs the same fns, collections, and subscribers you already know, stamped app: so Karsa can show, upgrade, and remove them as one unit.

That rule is the whole packaging model. An app is deconstructed: its parts are ordinary artifacts in their native collections — a fn in fn/, a subscriber in subscriber/, a collection, an agent user — each carrying app: app_<id> in its frontmatter. The app record is the anchor and the lens, never a container: nothing "lives inside" the app.

  • Where to look. Any list op takes { app: app_<id> } — karsa/subscriber/list { app } is the app's subscribers in place. karsa/app/inspect { id } assembles the whole thing in one call: the record, the parts grouped by collection, the exports. The stamp query IS the manifest — there is no separate manifest file to drift. In the web, stamped rows carry an app chip linking back to the app, and the app's page shows the assembled lens.
  • exports is the public surface. The record's exports: { fn: [...], collection: [...] } (singular keys) names what the app offers outward — later, its MCP tools/resources. A stamped part that isn't exported is an internal.
  • Stamped parts are read-only. update/delete on a stamped artifact refuse: owned by app <slug> — changes vanish on upgrade; pass force:true or fork it. force: true is the explicit "I accept that an upgrade clobbers this." To truly own a part, fork it: copy the artifact and drop the app: stamp — the copy is yours, and upgrades never touch it.
  • Removal is the same query. Disabling stops the process; the parts stay installed. Uninstall (coming) is delete-by-stamp — the confirmation lists exactly what goes, because the query is the manifest.

The controller converges — you never manage processes

A seeded System-project subscriber matches karsa/app/* and runs fn_app_controller. Flipping the toggle is just a patch (karsa/app/update {id, patch: {status: "enabled"}}); the controller compares desired (status) with actual (a live supervised process) and starts, stops, or no-ops. A crash restarts with capped backoff; a daemon restart re-converges every enabled app at boot. Disable and it gets a clean SIGTERM.

The actual state is a supervised exec_ in the System project — so the process shows up in the exec collection like any other run: pid, status, and its stdout/stderr as the exec log. Observability comes free.

Secrets by name

The record lists secret names, never values. They are resolved at spawn time and passed to the subprocess via env, never argv — nothing leaks through ps or the artifact tree. Where the value comes from depends on the secret: the tunnel's bind key and ingress secret are derived from the server's root key (which lives in the OS keychain), so they exist on no disk at all.

The free panel

The web UI's Apps page (/apps) lists every app record with its desired status, its actual state (running/stopped, from the live exec registry), the config summary, and an Enable/Disable button that patches the record. No per-app UI code — every app you mint appears there automatically.

The worked example: the tunnel

karsa remote enroll --gateway https://gw.karsa.dev   # one rpc: karsa/host/create
karsa remote up                                       # karsa/app/update {status: enabled}

Enrollment mints a host identity (the public entrypoint uuid) with the gateway, persists the public half as a host_ artifact and the bind key + ingress secret as undefined files, and upserts app/tunnel/index.md — disabled. Enabling it (CLI, /apps toggle, or the op) makes the controller spawn karsa-tunnel-client (installed beside karsa-server by karsa install) as a supervised exec_ with the secrets in its env. karsa remote down stops it. Re-enrolling re-points the same app at a fresh host without touching your enable/disable choice.

The generic process recipe — any binary, supervised

The tunnel needed its own recipe (key files, env secrets). Most sidecars don't: they are just "keep this command running." For those, the core controller has a generic process recipe — put a process block in the record's config and you're done:

config:
  process:
    cmd: ["caffeinate", "-dims"]   # argv — cmd[0] must be a bare binary name (PATH) or an absolute path
    cwd: /some/dir                 # optional
    env: { FOO: bar }              # optional, non-secret only

The daemon supervises it exactly like the tunnel: spawned once on enable, visible as an exec_ (pid + stdout/stderr log), crash-restarted with capped backoff, SIGTERMed on disable, re-converged at boot while enabled. A relative cmd[0] (./x) is refused loudly. Note the trust line: creating app records is an owner-level capability — the same trust as artifact writes; the recipe runs whatever the record says, uncaged.

The undefined-second example: @karsa/caffeinate

The second Karsa app is the whole pattern in one record — no code at all. @karsa/caffeinate keeps a Mac awake so Karsa's schedules run (macOS only; it supervises the system caffeinate CLI):

karsa install                                        # lands the package seed in the $KARSA_HOME/packages download cache
karsa/package/install {"package": "@karsa/caffeinate"}   # copies out of the cache: mints app/caffeinate/index.md in the System project, disabled

The install op reads the landed seed, mints the real app_ id (seeds may use vanity ids — they are rewritten), writes the record + any stamped parts, and mints the app's service user. Then flip it on from /apps. That's the entire app: one record whose config.process.cmd is ["caffeinate", "-dims"], converged by the machinery you already know.

Package scope — server or project

Every package declares a scope in its karsa.package.json: server for a machine-level capability, project for a per-project one. karsa/package/install enforces it: a server-scoped package (caffeinate, the tunnel app — anything that manages the machine) installs only into the System project, so "one per server" falls out of "the System project is one per server"; a project-scoped package installs into the project you name with the project arg. Templates are project-scoped by nature. Omitted scope means server — the pre-scope packages were all machine-level.

Minting your own app

karsa.package.json. Install it as a package — a seed tree src/app/<slug>/index.md + karsa.package.json via karsa/package/install (that's exactly what @karsa/caffeinate is): the installer mints the record's app_<ULID> id and writes the id-named dir app/app_<ULID>_<slug>/index.md for you (status: disabled, your config, your secret names, a README body; the seed's _slug becomes the handle). Hand-authoring the dir works too, but you must id-name it — a bare app/<slug>/ is rejected by the validator (the dir must carry the minted id). karsa/package/install. Pick the recipe. A plain "keep this command running" sidecar needs only config.process (the generic recipe above). The core controller also knows the tunnel shape. For anything richer set fn: to your own fn — the controller delegates every karsa/app/* event for that record to it as { event, app }, and your fn owns convergence (spawn a process as an exec_, reconcile some external state, whatever "running" means for your app). app_<ULID>. Stamp every part you install — the fn, its subscribers, any collection or agent user — with app: app_<id> in its frontmatter, and name your public surface in the record's exports. The stamp is what makes them one unit (show, upgrade, remove); it also makes them read-only to casual edits. app/app_<ULID>_<slug>/index.md. Put secret values in the secret store or a undefined file — only their names go in the record. status: disabled. Enable it with karsa/app/update. The events, the exec_ contract, and the /apps panel are already yours.

Gotchas & sharp edges (learned building @karsa-app/codex)

Building the first real caged app surfaced these. Some are fixed; the ones marked TODO are known non-idiomatic edges to smooth — write your app to them, and expect them to get friendlier.

  • A permission IS an op (spec_permissions: { docdb: [chat, msg] }MpermissionsGPXpermission/chat/*RDApermission/msg/* §permission/full). A fn declares the permissions it holds: permissions: { docdb: [chat, msg] } → permission/chat/*, permission/msg/* (a flat slug list works too). A held permission/msg/create may carry attrs that must equal the op's input params — that's how row-level scoping works ({ ownerId: user_X } = only your own rows). Owner holds permission/full.
  • A fn that spawns a subprocess declares allow: [run]. Fixed: the launcher now grants the OS perms the fn declares (allow: [run, net, ffi, sys]) on any launch path — so spawning no longer forces "detached." (Older daemons hardcoded --allow-run on the detached path only, so a Deno.Command fn had to be detach: true or it died with a bare permission error.)
  • msg (and other source: null collections) take { frontmatter: { … } }. karsa/msg/create { frontmatter: { chat_id, body, author } }, not top-level { chat_id, body }. The bare form errors with "requires chat_id and body" even though you passed them.
  • **A failed detached fn used to log nothing — the exec log was empty despite "open the exec log for detail." Fixed:** the failure reason now lands in the exec log. If you're on an older daemon and a detached run just says failed, that's why.
  • Reinstall used to DUPLICATE an app's records (it minted fresh ids each time). Fixed by the cage + reconcile-in-place: same slug → same id, state kept. If you reinstall to iterate, your fn keeps its id now.
  • A newly installed collection's CRUD can be unknown tool until the daemon restarts — package/install doesn't yet rebuild the per-project op catalog, so an app that writes to a collection it just installed (e.g. codex-context) may find the op missing. TODO (per-cage catalog, spec_package/installMundefinedXREXundefinedT §undefined.undefined): the cage's op catalog rebuilds with the cage. Until then, a fn's .catch around its own-collection writes keeps the turn alive.
  • An app writes as ITSELF — there is no write-as. Decided: msg/create { chat_id, body } (no author); _created_by = the acting persona-user, shown via its display name. An app may own multiple personas (one identity per persona, spec_authorMmsg/create { chat_id, body }Eauthor: user_agentKundefinedQundefinedC) — it just never writes as a user it doesn't own; a different driver CLI is a different app. (Earlier drafts had the runner pass author: user_agent — impersonation — which is retired.)
  • Addressing inside the cage is project/_/… for project resources. A bare karsa/msg/create from inside an app resolves in the cage and (correctly) fails — reach the project chat with karsa/project/_/msg/create { chat_id }. (Landing with spec_karsa/msg/createMundefinedXREXundefinedT §undefined.)
  • A subscriber needs its project_id (and, for an app, its cage context). A subscriber that ships without project_id is skipped as "malformed" at load — install must stamp it. (TODO: stamp the install-target project on caged subscribers.)
